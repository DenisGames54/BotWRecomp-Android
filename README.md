# BotW Recompiled: Android / Linux ARM64 (unofficial)

An unofficial **Android / Linux ARM64 port** of [BotWRecomp](https://github.com/IshaanKalra2103/BotWRecomp)
by Ishaan Kalra, which statically recompiles the PowerPC code of **The Legend of Zelda: Breath of the
Wild (Wii U)** to C++ and runs it on a Cafe OS runtime written for the project.

The original project targets iPhone and Apple Silicon Macs with Cemu's Latte GPU layer drawing through
Metal. This fork replaces that renderer with Cemu's **Vulkan** backend and builds on Linux ARM64, so
it runs on Android phones with a Vulkan driver (tested on Turnip / Adreno).

> [!IMPORTANT]
> **This repository contains no game files, no game code, no ROMs, no keys and no copyrighted or
> protected material of any kind.** It is only a tool. You need your own legally obtained copy of the
> Wii U game, dumped from your own console. The build recompiles *your* copy on *your* machine.
> There is no download-and-play package, and there never will be one. How you obtain and use the game
> files is your own responsibility. Do not ask for game files, keys or dumps in issues or discussions.
> The recompiled code (`generated/`) and PGO profiles are derived from the game: never commit or share them.

> [!WARNING]
> **This project is in an early stage and under active development.** Expect bugs, crashes, low
> frame rates and breaking changes. It is not ready for general use, and there is no APK or
> installer yet.

## Status

Early and experimental. Everything below was tested on a single device:

- **Device:** POCO F5 (Snapdragon 7+ Gen 2, Adreno 725)
- **Environment:** Debian ARM64 inside a [DroidSpaces](https://github.com/ShubhamPatilsd/droidspaces) container on Android, drawing to Termux:X11
- **GPU driver:** Mesa Turnip 26.3 (Vulkan 1.4)

What works:

- Full Linux ARM64 build (CMake + clang): [`linux/CMakeLists.txt`](linux/CMakeLists.txt).
- Vulkan renderer (Cemu's Latte Vulkan backend, vendored from Cemu commit `a53cf0e`) running on Turnip,
  from the title screen to the open world.
- **H.264 video playback** (cutscenes, tower videos) through a port of Cemu's `ih264d` decoder
  ([`runtime/src/h264/`](runtime/src/h264), [`runtime/third_party/ih264d/`](runtime/third_party/ih264d),
  generated by [`tools/port_h264.py`](tools/port_h264.py)). Without it the game crashes on video scenes
  (for example when activating the first tower). Tested: 60 fps, video and audio fine.
- Workaround for a Turnip shader-compiler crash caused by the `fmulz`/`fmadz` pattern in Cemu's
  non-IEEE multiply helper (`LatteDecompilerEmitGLSL.cpp`, marked `// BotWRecomp:`).
- Optional **PGO** (profile-guided optimization) build of the generated guest code: see [PGO](#pgo-profile-guided-optimization).
- [`linux/botw-run.sh`](linux/botw-run.sh): launcher that locks the GPU clock and pins threads to the big cores.
- An experimental second code generator pass, [`tools/codegen_v2.py`](tools/codegen_v2.py)
  (see [Experimental](#experimental-toolscodegen_v2py)).

Performance (honest numbers, early work, one device, one scene type; expect about +/-15% between
runs depending on temperature and where the scheduler puts the threads):

| Setup | Heavy open-world scene (3000-5000 draws/frame) | Light scenes |
| --- | --- | --- |
| Baseline build, stock clocks | 12-16 fps | |
| + GPU clock locked at maximum | 17-23 fps | 38-58 fps |
| + PGO build | about 24-34 fps (same save, same spot) | |

Profiling of the heavy scenes shows roughly 75% of CPU time in the recompiled guest code and about
14% in the renderer and driver. The front end is the bottleneck: L1 instruction-cache misses are about 22 per
1000 instructions (the generated code is about 10 ARM instructions per PowerPC instruction, 366 MB of
`.text`), so current work focuses on the generated code, not on the GPU.

Known gaps: performance is not yet comfortable in heavy scenes, shaders compile on first use
(hitches; a cache is kept in the user folder), only one device and one driver have been tested, DLC is
untested, `--capture` is not implemented on the Vulkan renderer, and there is no APK yet.

## What you need

- **An Android phone with a Vulkan 1.1+ GPU and a driver that exposes `geometryShader`,
  `independentBlend`, `VK_EXT_transform_feedback`, `VK_EXT_custom_border_color` and
  `VK_EXT_depth_clip_enable`.** Mesa Turnip does; the stock Qualcomm driver usually lacks
  `geometryShader`. Check with `vulkaninfo | grep -E "geometryShader|transformFeedback|customBorderColor|depthClipEnable"`.
  Only the POCO F5 (Adreno 725, Turnip) has been tested.
- **A Linux ARM64 environment with access to the GPU** (for now), for example Debian in DroidSpaces,
  plus a display server for SDL3 (for example Termux:X11).
- **Root** is recommended: the launcher locks the GPU clock through `/sys/class/kgsl`, which roughly
  doubles the frame rate in heavy scenes. Without root it still runs, just slower.
- **A PC or the phone itself** to run the recompiler (about 1 minute, then a build of 1 to 2 hours on a phone).
  About 10 GB of RAM is comfortable with `-j3`; allow about 5 GB of disk for `generated/` plus build trees.
- **A legal dump of the game, as a folder, in version v208.** Breath of the Wild for Wii U,
  **USA, update 1.6.0 (v208)**, dumped from your own console, as a folder containing `code/`,
  `content/` and `meta/` (the update's files copied over the base game's). Other regions and other
  versions are **not** supported: the recompiler and the patches are made for that exact executable.
  Check yours:

  ```bash
  sha256sum /path/to/game/code/U-King.rpx
  # ba58da5b95ce929e005d058ceb08b9b2788d1ab2bbc8a6c189bbadca0bb34d30
  ```

  Dump the game and its update from your own Wii U (for example with
  [Dumpling](https://github.com/emiyl/dumpling)). Nothing else is provided or supported here.

## Build (Linux ARM64)

```bash
# Dependencies (Debian/Ubuntu)
sudo apt install build-essential clang lld llvm cmake ninja-build git python3 python3-pip pkg-config \
    libvulkan-dev glslang-dev spirv-tools libspirv-tools-dev libsdl3-dev libfmt-dev libssl-dev \
    libzstd-dev zlib1g-dev libboost-dev libglm-dev libpng-dev libx11-dev libxcb1-dev
pip install cryptography        # needed by the recompiler (or use uv, as upstream does)

git clone https://github.com/DenisGames54/BotWRecomp-Android
cd BotWRecomp-Android
git checkout android-vulkan

# 1. Recompile your copy of the game to C++ (writes generated/, about 730 MB, about 1 minute)
python3 -I tools/recompile.py /path/to/game/code/U-King.rpx generated

# 2. Build (1 to 2 hours on a phone; -j3 keeps memory under control)
CC=clang CXX=clang++ cmake -S linux -B build -G Ninja -DBOTW_CPU=cortex-a78
cmake --build build --target BotWRecomp -j3

# 3. Run
export BOTW_GAME=/path/to/game
BOTW_BIN=build/BotWRecomp linux/botw-run.sh --fps 60 --scale 1
```

> [!NOTE]
> Use `-DBOTW_CPU=cortex-a78` on the Snapdragon 7+ Gen 2. `cortex-a710` makes clang emit SVE
> instructions, which this SoC does not expose, and the game dies with `Illegal instruction`.
> Set it to the newest core your CPU fully supports (check `grep Features /proc/cpuinfo`).

If you rebuild after changing the recompiler or `ppc.h`, expect a full rebuild of the guest code.

### PGO (profile-guided optimization)

A PGO build of the generated guest code measured about +25 to +40% in the heavy scenes. The profile is
tied to the generated code, so recollect it whenever you regenerate `generated/` with different code
generation. **Never commit `.profraw` or `.profdata` files** (they come from the game).
Options are in [`linux/CMakeLists.txt`](linux/CMakeLists.txt):

| CMake option | Meaning |
| --- | --- |
| `-DBOTW_PGO=gen` | instrumented build (about 30% slower; writes `.profraw` on exit, also on a fatal error) |
| `-DBOTW_PGO=use` | optimized build using a merged profile |
| `-DBOTW_PGO_DATA=<file>` | the merged `.profdata` for `BOTW_PGO=use` |
| `-DBOTW_CPU=<core>` | `-mcpu` for the generated code (default `cortex-a710`, see the note above) |

```bash
# 1. instrumented build
CC=clang CXX=clang++ cmake -S linux -B build-pgo-gen -G Ninja -DBOTW_CPU=cortex-a78 -DBOTW_PGO=gen
cmake --build build-pgo-gen --target BotWRecomp -j3

# 2. play for 10-20 minutes: walk, climb, glide, fight, open menus, watch a cutscene.
#    Quit by closing the window or with Ctrl+C: the profile is written on exit.
mkdir -p ~/pgo
BOTW_BIN=build-pgo-gen/BotWRecomp LLVM_PROFILE_FILE=$HOME/pgo/botw-%p.profraw linux/botw-run.sh --fps 60 --scale 1

# 3. merge (on Debian the tool is /usr/lib/llvm-19/bin/llvm-profdata)
llvm-profdata merge -output=$HOME/pgo/botw.profdata $HOME/pgo/*.profraw

# 4. final build (about 2 hours)
CC=clang CXX=clang++ cmake -S linux -B build-pgo-use -G Ninja -DBOTW_CPU=cortex-a78 \
    -DBOTW_PGO=use -DBOTW_PGO_DATA=$HOME/pgo/botw.profdata
cmake --build build-pgo-use --target BotWRecomp -j3
```

The more varied the play session, the better the profile: code that never ran during profiling is
placed in cold sections and runs slower if you reach it later.

## Running

```bash
linux/botw-run.sh [--fps 30|60] [--scale N] [--headless] [--seconds N]
```

[`linux/botw-run.sh`](linux/botw-run.sh) is configured through environment variables:

| Variable | Default | Meaning |
| --- | --- | --- |
| `BOTW_BIN` | `build-pgo-use/BotWRecomp` if it exists, else `build/BotWRecomp` | binary to run |
| `BOTW_GAME` | `./game` | game folder (`code/`, `content/`, `meta/`) |
| `BOTW_USER_ROOT` | `~/botw-user` | saves, `settings.ini`, shader cache, `runtime.log` |
| `BOTW_GPU_LOCK` | `1` | lock the Adreno clock at its maximum (root; restored on exit) |
| `BOTW_CPUS` | `4-7` | CPU list for `taskset`; empty disables it. `4-7` are the A710/X2 cores of a Snapdragon 7+ Gen 2 |
| `BOTW_NOIDLE` | off | `1` disables deep CPU idle on cores 4-7 (no measurable gain so far) |
| `BOTW_THP` | off | `1` asks for transparent huge pages for guest memory (needs `echo madvise > /sys/kernel/mm/transparent_hugepage/enabled`; little gain on fragmented phones) |
| `BOTW_CRIT_CPUS`, `BOTW_GPU_CPUS` | unset | pin the game's critical threads / the renderer thread to a CPU list (no gain measured) |
| `DISPLAY` | your environment | X11 display for SDL3 (for example Termux:X11) |

Command line options:

| Option | Meaning |
| --- | --- |
| `--fps 30` / `--fps 60` | frame-rate mode. Any value of 60 or more is treated as 60 (`--fps 120` is the same as `--fps 60`). 30 mode waits two vblanks per frame, so a game that runs at 15 to 20 fps shows as 10 fps; judge performance in 60 mode |
| `--scale N` | internal render scale (`1` is native 720p; `0` fits the display). It also lives in `settings.ini` |
| `--headless` | no visible window (smoke tests) |
| `--seconds N` | quit after N seconds (benchmarks) |

The log is written to `$BOTW_USER_ROOT/runtime.log`; the `[gpu] ... fps, N draws/frame` lines are the
frame-rate reports. Settings are stored in `$BOTW_USER_ROOT/settings.ini` and are rewritten whenever you
change an option in the in-game menu (F1, the touchpad, or L3+R3), so they persist between runs:

| Key | Values |
| --- | --- |
| `fps` | `30` or `60` |
| `scale` | render scale, `0` = fit the display (applies at the next launch) |
| `display` | `0` fit (letterbox), `1` stretch, `2` fill (crop) |
| `filter` | output scaling: `0` bilinear, `1` bicubic (default), `2` hermite, `3` nearest |
| `gyro`, `rumble`, `layout`, `show_fps`, `volume`, `touch`, `touch_hidden` | see the in-game menu |

Keyboard layout: **E** = A, **Left Shift** = B, **Space** = X, **F** = Y, **Q** = ZL, **R** = ZR,
**1** = L, **3** = R, **Enter** = +, **Tab** = -, **arrow keys** = D-pad, **C** / **V** = stick presses,
**W A S D** = left stick, **I J K L** = right stick, **F1** = settings menu.

### Benchmarking tips

Frame rate varies by about +/-15% from run to run (temperature, which core the busiest thread lands on).
To compare two builds, use the same save at the same spot, let the scene settle, and average several runs.
`perf stat -p <pid> -- sleep 15` works on the phone and shows whether you are front-end bound.

## Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| `Illegal instruction` right after start | the `-mcpu` of the build uses instructions your CPU lacks (SVE on a Snapdragon 7+ Gen 2). Rebuild with `-DBOTW_CPU=cortex-a78` |
| `SDL_Init failed: No available video device` | no X11/Wayland display. Start your display server (Termux:X11) and set `DISPLAY` |
| `Vulkan loader (libvulkan.so.1) not available` or a driver without `geometryShader` | install/enable the Turnip Vulkan driver in your Linux environment |
| a crash inside `libvulkan_freedreno.so` with `Unhandled ALU op` | a Turnip shader-compiler bug. The known `fmadz` case is worked around; delete `$BOTW_USER_ROOT/cache` after updating shaders and report the op |
| `FATAL: unimplemented import ...` | the game called a Cafe OS function this runtime lacks. Report it with the full log |
| `THP madvise` returns `0` but `AnonHugePages` stays tiny | the kernel could not find free 2 MB blocks; THP then has no effect |

## Experimental: `tools/codegen_v2.py`

A small, reversible set of code generation changes. Run from the repository root, then regenerate
`generated/` and rebuild:

```bash
python3 tools/codegen_v2.py ea call      # safe: keeps the PGO profile valid
python3 tools/codegen_v2.py hle          # also drops the inline HLE trace branch; recollect the PGO profile after this
```

| Step | What it does | Measured |
| --- | --- | --- |
| `ea` | computes `rA + d` in 64 bits so the host folds the displacement into its addressing mode; adds a guard page below guest memory | about -2% instructions in one generated unit |
| `call` | indirect calls (`bctrl`) hit the text table directly | small |
| `hle` | removes the inline `g_trace_hle` check from every HLE call (`-DBOTW_TRACE_HLE` brings it back) | not measured yet |
